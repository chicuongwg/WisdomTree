# Stage 4B0 — Project Test Isolation & Fixture Contamination Audit

Result: **PASS**

Date: 2026-09-01 (Asia/Ho_Chi_Minh)

## 1. Root cause

### Observed execution path before this change

1. `npx tsx tests/integration/project-foundation.test.ts` imported the shared application database module.
2. When `DATABASE_URL` was absent, that module defaulted to `postgres://...@localhost:5432/wisdomtree` (`src/db/index.ts:5-19`).
3. The direct test entrypoint called `run()` without any database-isolation assertion (`tests/integration/project-foundation.test.ts:211-215`).
4. `run()` created a Project/Team Space, manager membership, audit rows, a legacy Team Space, viewer membership, a Folder, and a Project update (`tests/integration/project-foundation.test.ts:55-79`, `tests/integration/project-foundation.test.ts:90-134`).
5. Its `finally` block cleaned up only the temporary database function and trigger used for the atomicity assertion. It did not delete the Project, Space, membership, Folder, or audit fixtures (`tests/integration/project-foundation.test.ts:169-208`).
6. The suite runner previously only discovered/imported test files and did not configure or validate a test database. Package scripts invoked that runner without a test-database environment contract (`package.json:28-33`).

**OBSERVED ROOT CAUSE:** A direct Project integration-test invocation inherited the application's normal local default database, and the test deliberately retained uniquely named fixture rows. There was no fail-closed database guard.

Repository evidence does not preserve whether each run was launched directly or through the old unguarded suite runner; both paths could target `wisdomtree` when `DATABASE_URL` was absent.

## 3. Test isolation change

Added one shared test-database safety module: `tests/db-safety.ts`.

Stateful suite contract:

```text
TEST_DATABASE_URL must be explicit
→ database name must contain a distinct "test" segment
→ runner assigns it to DATABASE_URL before importing application code
→ otherwise refuse execution
```

- `configureIsolatedTestDatabase()` validates `TEST_DATABASE_URL` and assigns it before the shared DB pool can be imported (`tests/db-safety.ts:20-30`, `tests/run-all.ts:13-20`).
- `assertIsolatedTestDatabase()` protects direct stateful test-file execution by requiring explicit, exactly matching `DATABASE_URL` and `TEST_DATABASE_URL` values (`tests/db-safety.ts:32-42`).
- `tests/setup.ts` invokes the direct-execution assertion at module load, before its session/principal helpers or a test's `run()` can create state (`tests/setup.ts:1-8`).
- The cron API integration test does not use shared setup, so it invokes the same guard explicitly before dispatch (`tests/integration/api.test.ts:1-7`).
- Test documentation now requires create/migrate/seed/run/dispose against an isolated database (`tests/README.md:31-36`, `tests/README.md:57-72`).

No application database resolution, service, schema, route, authorization, or domain behavior changed.

## 5. Fail-closed guarantee

Verified behaviors:

1. Bare direct Project invocation exits before the test's `run()` with:

   ```text
   Refusing stateful tests: DATABASE_URL and TEST_DATABASE_URL must explicitly match an isolated test database.
   ```

2. Bare canonical integration invocation exits before test imports with:

   ```text
   Refusing stateful tests: TEST_DATABASE_URL is required.
   ```

3. Supplying `TEST_DATABASE_URL=postgres://localhost/wisdomtree` is also rejected before connection/mutation with:

   ```text
   Refusing stateful tests: database "wisdomtree" is not explicitly named as a test database.
   ```

4. A safe run used `wisdomtree_test_stage4b0_20260901`, applied migrations, seeded only that database, ran the requested suites, and disposed the database afterward.

The safety guarantee does not depend only on remembering a command: the runner and direct stateful setup refuse unsafe execution.

## 9. Remaining risks

1. Database provisioning/disposal is explicit rather than automated by the package script. This keeps the change narrow, while the fail-closed guard prevents fallback to the normal DB. CI/operator workflows must create, migrate, seed, and dispose their test database.
2. Tests intentionally retain fixtures inside their disposable database. This is safe only because the database is isolated and discarded; individual test rollback/cleanup was not introduced.
3. `tests/e2e/global-setup.ts` has a separate DB/session setup path and was not part of the requested integration/use-case/privacy hardening. It should be audited before claiming the same isolation guarantee for Playwright.
4. Existing fixture rows remain in `wisdomtree` pending explicit cleanup authorization.
5. The database-name check is a safety signal, not proof of ownership. It is combined with the explicit `TEST_DATABASE_URL` contract; credentials and database provisioning still remain operator-controlled.
