# Technology Stack

Status: accepted by the owner on 2026-07-19. This file is no longer a proposal; changes to a layer choice require a new decision-log entry.

## Purpose
- Define the V1 implementation stack, so backend, worker, and frontend work can begin without reopening platform-level infrastructure decisions.
- Keep the stack buildable and operable by one developer plus AI agents, with local-only AI and no paid API dependency.

## In Scope
- Application, worker, database, storage, identity, and AI runtime choices.
- The search and embedding approach across phases.
- Constraints that follow from the one-operator, local-only posture.

## Out of Scope
- Exact library and framework version pins.
- Deployment automation scripts (see [`deployment-topology.md`](./deployment-topology.md)).
- Feature-level design.

## Decisions
- This file is the accepted stack; where a choice was left open (for example TipTap versus Milkdown), the named default stands until implementation proves otherwise.
- The stack must run as the existing VPS-plus-worker topology and be operable by a single technical person.
- AI is local-only through Ollama on the worker host, with no paid API dependency and no hard dependency on any external AI service.

## Dependencies
- Runtime topology in [`deployment-topology.md`](./deployment-topology.md).
- Module map in [`../platform/module-map.md`](../platform/module-map.md).
- Non-functional targets in [`../requirements/non-functional-requirements.md`](../requirements/non-functional-requirements.md).

## Acceptance Criteria
- An implementer can start the app, worker, and database with a clear stack choice for each layer.
- The search plan is explicit about what ships in V1 versus Phase 1.5.
- Every AI-dependent feature has a defined behavior when AI is unavailable.

## Proposed Stack

| Layer | Proposal | Rationale and tradeoff |
| --- | --- | --- |
| App and API | TypeScript full-stack (one framework serving API and server-rendered UI) | One language across app and UI keeps a solo developer productive; a single deployable matches the modular monolith. |
| Frontend editor | TipTap or Milkdown, persisting Markdown | WYSIWYG feel for non-technical writers while keeping Markdown as the stored format; see [`../ui/design-system.md`](../ui/design-system.md). |
| Worker | Python | Best ecosystem for OCR, document rendering, and later embeddings; runs on the separate worker host. |
| Database | PostgreSQL | Canonical tree content, spaces, catalog, and workflow state; also hosts full-text search in V1. |
| Search (V1) | PostgreSQL full-text search | No new infrastructure; adequate for a small team and multi-domain content. |
| Semantic search (Phase 1.5) | pgvector in the same PostgreSQL, embeddings from a local Ollama model | Adds meaning-based finding with zero new services and no paid API. |
| Object storage | S3-compatible | Original files and evidence artifacts, as already specified. |
| Queue | Redis | Job orchestration between app and worker, as already specified. |
| Identity | Google OIDC | No new accounts; the team already has Google. |
| AI runtime | Ollama, local-only | OCR support, indexing, document finding, and cited answers, all on the worker host with no paid dependency. |
| Document rendering | Pandoc-class converter on the worker | Node Markdown to docx and pdf. |
| Publishing | Quartz-class static site in the content repo CI | Selective read-only public pages without an app-runtime module. |
| Email and Zalo | Email provider plus Zalo Official Account | Outbound notifications; see [`notifications.md`](./notifications.md). |

## AI Approach and Fallback
- V1 ships full-text search and local OCR only; no feature requires an external AI service.
- Phase 1.5 adds local embeddings for semantic finding, stored in pgvector, generated by the worker's Ollama models.
- Phase 1.5 or 2 adds the AI Librarian: answers over stored documents that cite and quote sources through the existing provenance and excerpt model.
- Every AI-dependent feature degrades cleanly: if the worker or Ollama is unavailable, storage, catalog, knowledge, and full-text search continue to work.

## One-Operator Constraints
- Favor a single deployable and a single database over distributed components a lone operator cannot easily run.
- Prefer boring, well-documented technology over novelty, since the operator is also the sole maintainer.
- Keep the worker replaceable behind the job contracts in [`integration-contracts.md`](./integration-contracts.md), so OCR or rendering engines can change without touching the app.
